今天花了一段时间让 AI Agent 帮我修一个 Slack 工具的 bug。整个过程我一行代码没写。但我也没闲着——我做的事是：发现它忽略的安全漏洞、否掉它提的设计方案、问它有没有 race condition、告诉它下载路径要放在 session 目录下而不是别处。

这个过程让我意识到一件事：**和 Agent 协作，人的工作性质变了——从"下指令"变成了"纠偏"。**

## 工具 vs. 合作伙伴

用工具的时候，你是主动的那一方。你想要什么，你告诉工具，工具执行。工具不会跑偏，因为它根本不会自己跑。

但 Agent 不一样。你给它一个方向，它就开始动了——clone repo、读代码、写 fix、准备 PR。它在跑，你在旁边看。问题是它跑的路不一定是你想要的那条。

所以你的工作变成了：**观察它在往哪儿走，判断对不对，在它走远之前把它拉回来。**

这不是在"使用"一个工具，更像是在带一个很能干但需要方向感的人。

## 纠偏比下指令更难

听起来好像省事了——代码不用写了。但纠偏其实有它自己的难度。

你得看得懂它在做什么，才能判断对不对。今天那个 session，Agent 提了一个用 `ContextVar` 管理 session 目录的方案，听起来挺合理，但我的直觉是多线程环境下可能有问题。得先问清楚再说。结果深问下去，发现其实 ok，因为底层是单线程的事件循环。这个判断过程，比自己写代码花的脑力少吗？不一定。

而且下指令可以很精确，纠偏往往是模糊的。"这个设计我不喜欢，重新想"——这句话说起来容易，但要让 Agent 真正理解你不喜欢的是什么、下一个方案应该往哪个方向走，需要反复迭代。那个 session 里，光这一个下载路径的问题，来来回回说了六轮。

## 主动权在哪里？

以前写代码，主动权完全在你：你写什么，系统就是什么。

现在用 Agent，主动权分散了。Agent 有它自己的判断，它会选择它认为合理的实现方式。你保留的是**方向权和否决权**，但执行权交出去了。

这个转变值得认真对待。因为如果你不善于行使方向权和否决权，Agent 的能干反而会成为问题——它很快就跑出去很远了，但方向是错的。

## 这意味着什么

我觉得和 Agent 协作需要的核心能力，不再是"能写代码"，而是：

- **快速判断对错**：看懂 Agent 的方案，知道它的风险点在哪
- **清晰表达意图**：不是"帮我写个函数"，而是"我要的是这个效果，约束是这些，你来决定怎么实现"
- **知道什么时候踩刹车**：Agent 跑得快，但错了也快，要有敏感度

这和带人很像。带一个很能干的人，你不需要手把手，但你需要非常清楚自己要的是什么，以及什么时候他的方向偏了。

也许这就是为什么用 Agent 越来越感觉像在管理，而不像在编程。
