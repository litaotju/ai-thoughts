# 元问题与程序员的角色转变

春节期间，我花了几天时间用 Claude Code 搭了一个以 Slack 为中心、7×24 小时待命的 agent（链接在结尾）。一方面是拿这个项目练手，学习 Claude 的使用技巧；另一方面是工作需要——有很多 routine 的事情确实需要一个全天候在线、mobile-friendly 的 assistant 来做 offloading：approve PRs、日常 triage bugs、翻阅和 catch up Slack channels。

七天时间，亲眼见证这个业余项目从一个 one-shot 调用 `claude --print` 的 Slack bot，成长为一个功能完备、安全（自认为）、AI-native 的 agent router/orchestrator。有几个晚上因为和 Claude 以及自己的 baby agent 交互而兴奋得睡不着。

七天的高强度 agent 交互也刷新了很多我之前的认识。以下是一些浅见，供大家参考，说得不对的地方欢迎来喷。

> **一点题外话：** Claude 本身的使用也值得祛魅。skills、commands、sub-agent、teams、MCPs——这些术语听起来高大上、种类繁多，但在我的使用体验里，它们完全是非核心的。一开始不需要掌握这些概念，跟着用就好，一切都会水到渠成。

---

## 一、Claude 的自举能力，以及软件的元问题

最深的感受是 Claude 的 bootstrap 能力强得出乎意料。所有关于 Claude 自身使用的问题——包括我自己交互式调用 Claude 开发，以及让自己的 agent 调用 Claude Agent SDK——我一行官方文档都没有主动查过。遇到问题，从最开始精心 prepare context 和格式化问题，到后来直接把 log paste 进去，甚至什么都不说让它自己去找 log，直观感受是 95% 的情况都能解决，区别只在于 tool call 的次数和 token 成本多少。

这件事刷新了我对软件分发方式的认知：文档、界面、按钮，甚至 API，都不再是给人看的了，而是给 agent 看的。你真正关心的，是最开始想用软件解决的**元问题**，而不是软件本身的使用方式。

更进一步：如果一个软件不存在，当你把问题抛给 Claude，它可以帮你生成一个 one-off 的、用完即弃的小工具——"软件"的定义在这里可大可小，也许更准确的说法是 *function*。我无数次看到 Claude 用 Python 代码处理 tool call 返回的大块文本，生成精简、结构化的数据再喂给自己作为 context。

这让我想到一个问题：软件工程师归根结底是在开发工具来解决现实问题。如果有一天，开发工具这件事本身可以被完全自动化——问题入 agent、答案出 agent——那程序员的价值还在哪里？

---

## 二、AI 的编码能力已远超人类；但人类还有两块地盘

AI 的编码能力和速度远远超越了人类，这一点我不再有任何疑问。但经过这七天，我认为目前人类程序员仍然比 AI 强的地方有两个：**私有知识**和**连接（connection）**。

**私有知识**是指那些没有被写下来、没有被上传、存在于人脑和组织记忆中的信息。哪个 team 的哪个人真正懂这块代码、某个架构决策背后不成文的原因、某个 bug 三年前已经修过但没有留下 trace——这些 context AI 拿不到，只有人知道。

**连接**是指跨越系统边界的协调能力。很多真正重要的工作不是写代码本身，而是让正确的人在正确的时间做正确的决定。这需要信任、组织关系和沟通判断力——目前 AI 还没有这些。

所以，程序员真正应该保有的，是充当这两者之间的 **bridge**：把私有知识和关键判断注入 agent 的 context，让 AI 得以处理那些本来只有人才能处理的问题。

---

## 三、拥抱 AI 与否，差距正在被拉开

在现阶段，程序员和程序员之间的产出差距可以被拉得非常大，也可以被磨得更平——这听起来矛盾，但我认为两者都在同时发生。

拥抱 AI，意味着你拥有了很多并行处理事情的"分身"。你要做的是授权和验收，而不是亲自动手每一行代码。不拥抱 AI 的人，会被无情地拉开差距。

但与此同时，AI 也在磨平某些技能壁垒——以前需要很强底层功底才能做到的事情，现在初级工程师借助 AI 也可以快速完成。这意味着纯粹的执行力和编码速度不再是护城河。

真正的护城河变成了：**你能不能提出正确的元问题，你有没有足够的私有知识和 connection 去验证 AI 的输出是否真的解决了问题。**

这件事让我觉得，程序员这个职业本身没有消失，但它的核心正在从"写代码"变成三件事：**定义问题、注入 context、验证结果**。

- **定义问题**意味着和现实世界的连接——你得知道客户或 stakeholder 真正想解决的是什么，而不是他们描述的表面需求。
- **注入 context** 的关键同样是连接。公司内外部很多系统还没有完成从"以人为中心"到"以 agent 为中心"的转变，这些信息的缺口只能由人来填补。
- **验证结果**意味着责任。当 agent 做出的决策无法自己承担后果时，你是最终的负责人。

---

## 四、程序员应该有"老板"心态

把上面三件事合在一起看，会发现这其实是一个 manager 或 owner 最应该关注的问题，而不是一个执行者的问题。所以我认为，在 AI 时代，每个程序员都应该建立起一种"老板"心态：给定一个 agent 的算力/token 预算，你的目标是让这笔投入产出最大化。

这要求一些具体的能力：把任务交代清楚，避免 agent 反复返工；在 agent 的能力边界内注入足够的 context，让它有条件完成任务；提前做风险判断，确认结果是可验证的；并对最终产出的现实世界影响负责。

这个听起来很像是项目管理，但本质上更接近投资决策——你在用有限的预算，押注一个 agent 能不能解决一个真实问题。

---

## 五、更远的未来：人类成为纯粹的消费者

不过，即便是"老板"这个角色，我认为也只是过渡阶段的产物。说完这些对程序员当下能做什么的判断，不妨再往远处看一眼。

随着 agent 与现有系统的集成越来越深、算力成本持续下降、基座模型越来越智能、人们对 AI 的信任逐步建立，"定义问题、注入 context、验证结果"这三件事本身也会被进一步自动化。那个时候，软件的元问题会退化成人本身的需求问题：你想要什么，而不是你会做什么。

到那个阶段，不管是软件工具还是其他信息产品——音乐、视频、电影——生成的成本都会接近于零，速度接近于即时。人类会成为完全意义上的消费者。定义一个人的，不再是他掌握了哪些技能，而是他有怎样的品味、偏好和欲望。

这个结论有点让人不安，但我觉得值得提前想清楚。

## 番外：AI 安全，没那么可怕，但要想清楚

最开始我的安全模型很简单：只允许 user 执行 read-only 的命令（请原谅我对于"安全"的认知，最开始我想的只是不要让 agent 把我服务器上面的数据和代码搞坏）。但和 agent 交互几轮之后，我意识到这远远不够。

最让我担心的是 prompt injection。我的 assistant 是以自己的 user ID 跑在 server 上、并授权了 MCP 的，所以理论上任何我能操作的东西，这个 agent 也能操作。如果开放给其他人交互，就有被滥用的风险——写操作、更新信息系统、发送消息、读取 token、读取未授权信息。

我最终采取了几层措施：role-based tool authorities + hard-coded enforcement，以及 sensitive information 的 pre/post agent call filter，在 agent 可用工具的源头和执行前后 hook 住，防止 assistant 被他人滥用。这些措施目前都在 LLM 调用之外硬编码，所以我不是非常担心 LLM 本身的错误决策导致问题。

尽管如此，以我的直觉，AI 调用系统工具的能力之强，让我毫不怀疑它能找到方法绕过我明面上禁止的事情。归根到底，AI 系统的安全取决于使用者和 agent/model 的**意图**。对于把 agent 部署到公司内部，还是要相信大家的意图是善意的。如果发生了更底层的安全问题——比如有人已经拿到了你的 token 或者能登录到你的 server——那 agent 和传统工具的安全性同样会被 compromise，这不是 AI 特有的问题。
